# fabric-bridge Delta

## Purpose

Normative contract for the Phase 3 Fabric server bridge: how a real Minecraft
26.2 Fabric server consumes libhyperchunk over Java FFM at region-batch
granularity, serves canonical chunks, detects unsupported worldgen
configurations and yields to vanilla, and joins the parity gate chain as the
third gated consumer.

## ADDED Requirements

### Requirement: Region-batch FFM consumption

The bridge SHALL consume libhyperchunk exclusively through the public C
facade over Java FFM (JEP 454, final in Java 25; ADR-006 D4), and every FFM
crossing SHALL be at region-batch granularity
([core-abi](../../../../specs/core-abi/spec.md)). The bridge MUST NOT
implement its own chunk scheduling or allocation: scheduling policy is
selected through the library contract
([scheduler](../../../../specs/scheduler/spec.md)), and all generation-path
memory is caller-provided buffer backing owned by the bridge, never freed by
the core.

#### Scenario: Bridge granularity and binding audit

- **WHEN** the bridge's native binding layer is reviewed
- **THEN** every bound symbol is declared in the public facade header, every
  downcall is per region batch (or batch lifecycle/init/teardown), and no
  per-chunk, per-node, or per-sample crossing exists

#### Scenario: No Java-side scheduling

- **WHEN** a bridge change proposes ordering, partitioning, or parallelizing
  stage work on the Java side (e.g. per-chunk worker tasks feeding the core)
- **THEN** it is rejected: the core owns batching and the scheduler
  (ADR-003 D3)

### Requirement: Canonical output served through the vanilla load path

Chunks served by the bridge SHALL be the core's canonical serialized output
for the containing region, injected through the server's stock chunk load
path as fully generated chunks. The bridge MUST NOT substitute per-stage
generation results inside the vanilla generation pipeline: a chunk is either
served whole from bridge-generated region data or generated entirely by
vanilla.

#### Scenario: Pregenerated region is served without regeneration

- **GIVEN** a region pregenerated by the bridge
- **WHEN** the server loads chunks of that region
- **THEN** every chunk is served from the bridge-generated data through the
  load path, reaches vanilla status `minecraft:full`, and no worldgen stage
  recomputes its content

#### Scenario: Per-stage substitution is rejected

- **WHEN** a bridge design proposes returning native results from individual
  generation-stage calls inside the vanilla pipeline
- **THEN** it is rejected: per-stage substitution reintroduces
  per-chunk-per-stage boundary traffic and mixed-pipeline nondeterminism

### Requirement: Unsupported-configuration detection and yield

Before activating for a dimension, the bridge SHALL verify that the
dimension's effective worldgen configuration is within core scope: the
vanilla noise generator with overworld settings, and worldgen data (pack
format 107.1) that the core's initialization accepts in full. On any
unsupported configuration — a construct the core's init rejects, a
Java-registered worldgen extension, a non-overworld dimension, or a
chunk-system-rewriting mod — the bridge MUST stay inactive for that
dimension and yield generation entirely to vanilla. Partial activation is
forbidden; yield granularity MUST NOT be smaller than a whole chunk
([generation-pipeline](../../../../specs/generation-pipeline/spec.md)
whole-chunk fallback), and the MVP yields whole dimensions.

#### Scenario: Java-registered feature present

- **GIVEN** a mod registers a Java-coded worldgen feature
- **WHEN** the server starts with the bridge enabled
- **THEN** the bridge logs one clear yield line, stays inactive for the
  affected dimension, and vanilla generation proceeds unmodified

#### Scenario: Core init rejects datapack content

- **GIVEN** an enabled datapack containing a worldgen JSON construct the core
  cannot interpret
- **WHEN** the bridge feeds the effective worldgen data to core
  initialization
- **THEN** init fails with an error message, the bridge yields, and no
  partially-configured native generation occurs

### Requirement: Inert by default, vanilla never broken

The bridge SHALL be completely inert unless explicitly enabled: with the mod
installed but not enabled, server behavior is unchanged. Bridge-side
failures MUST NOT corrupt or alter vanilla generation output: on any error
in bridge code paths, the affected regions are served or regenerated by
vanilla, and the failure is logged rather than propagated into the chunk
pipeline.

#### Scenario: Disabled boot

- **WHEN** the server boots with the bridge mod installed but not enabled
- **THEN** no bridge hook takes effect and generation behavior is identical
  to a stock server

#### Scenario: Native batch failure mid-pregen

- **GIVEN** a native batch call that fails or aborts pregeneration of a
  region
- **WHEN** the server later needs chunks of that region
- **THEN** no partial bridge output is visible to the server and vanilla
  generates the region

### Requirement: Bridge parity gate

Bridge-served output SHALL join the parity gate chain as a third gated
consumer. With the bridge generating region r.0.0 (seed 1234567890) in
REPLAY mode from the golden bundle's order manifest, a quiet-server load and
save round trip of all 1024 chunks MUST yield the pinned golden canonical
payload hash (canonical hash definition and pins:
[worldgen-parity](../../../../specs/worldgen-parity/spec.md)). FREE-mode
bridge output MUST be verified against the FREE own-v1 pin only and MUST
NOT be bit-compared against vanilla golden 07+ dumps. The gate is local-only
(golden data and a server install) and is required for bridge-affecting
changes.

#### Scenario: REPLAY round trip equals golden

- **WHEN** `bridge_parity_gate.sh` runs the REPLAY pregen, loads all 1024
  chunks on a quiet server, saves, and hashes the emitted region
- **THEN** the canonical payload hash equals the pinned golden hash

#### Scenario: FREE round trip equals own-v1

- **WHEN** the same round trip runs with FREE-mode pregen
- **THEN** the canonical payload hash equals the pinned own-v1 hash, and no
  comparison against vanilla golden 07+ dumps is attempted

### Requirement: Runtime and packaging contract

The bridge SHALL run on a stock Fabric server at the pinned target
(Minecraft 26.2, Java 25, pinned Fabric loader), shipping its native library
inside the mod artifact for linux-x86-64 initially. The shipped native
library's dependency surface MUST remain libc/libm/pthreads only, with ISA
selection via runtime dispatch so the artifact runs on hosts without AVX
extensions. On unsupported platforms or when native access is unavailable,
the bridge MUST stay inert with a single clear log line rather than fail the
server.

#### Scenario: Stock server boot and handshake

- **WHEN** a fresh Fabric 26.2 server with the mod jar and the enable flag
  boots on Java 25 with native access granted
- **THEN** the bridge loads its packaged native library, logs an ABI version
  handshake, and reports readiness

#### Scenario: Native library dependency audit

- **WHEN** `ldd` inspects the shipped native library
- **THEN** no dependency beyond libc/libm/pthreads appears
