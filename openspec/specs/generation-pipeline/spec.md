# generation-pipeline Specification

## Purpose

생성 파이프라인의 normative SSOT: 풀 파이프라인 범위(11스테이지), 타겟 버전
핀(26.2), 데이터팩 스키마 호환과 바닐라 fallback 계약. 근거·수치·결정 역사는
[context.md](context.md).

## Requirements

### Requirement: Full pipeline, eleven stages

The implementation MUST cover the full vanilla chunk pipeline — all 11
statuses from `structure_starts` to `full` (noise, surface rules, carvers,
features, lighting, spawn, full promotion included) — not a terrain-only
subset (ADR-002 D2). Every stage runs in the C core; there is no JVM in the
generation path.

#### Scenario: Full-status region

- **WHEN** hyperchunk generates region r.0.0
- **THEN** every chunk reaches vanilla status `minecraft:full` and the
  full-region parity gate ([worldgen-parity](../worldgen-parity/spec.md))
  passes over the complete pipeline output

### Requirement: Single-version pin — 26.2

The target version SHALL be pinned to exactly one vanilla release, recorded
in the `TARGET_VERSION` file (currently `26.2`, data version 4903, data pack
format 107.1; ADR-006 D1). Scope per ADR-002 D4: overworld only; structures
are placed (through their placement step) but not jigsaw-assembled; Nether,
End, and a version matrix are out of scope.

#### Scenario: Version-scoped behavior question

- **WHEN** vanilla behavior differs between 26.2 and any other version
- **THEN** 26.2 behavior as observed in its unobfuscated server jar and
  extracted data is authoritative, and no compatibility path for other
  versions is added

### Requirement: 26.2 primary evidence rule

Ported algorithms MUST be grounded in the unobfuscated 26.2 server bytecode
and the 26.2-extracted datapack JSON (`reference/`), not in wiki articles or
pre-26.x reference implementations (ADR-006). Decompiled/unobfuscated source
MUST NOT be copied as code; name references and algorithm understanding only.

#### Scenario: Reference conflict

- **GIVEN** a wiki page or cubiomes describing pre-26.x behavior that
  conflicts with the 26.2 bytecode or extracted JSON
- **WHEN** the port is written
- **THEN** the 26.2 evidence wins and the discrepancy is noted in the task
  notes

### Requirement: Datapack worldgen schema as the compatibility surface

The core MUST accept datapack worldgen JSON (`noise_settings`,
`density_function`, `placed_feature`, and the related worldgen registries) at
the 26.2 schema (pack format 107.1) as its compatibility interface
(ADR-003 D4). A datapack expressible entirely in worldgen JSON
(Terralith-class) MUST generate with the same parity guarantee as vanilla
data.

#### Scenario: Pure-JSON datapack

- **GIVEN** a worldgen datapack that registers only data-driven JSON
  (no Java-registered features)
- **WHEN** hyperchunk generates with that datapack active
- **THEN** output matches the vanilla-with-that-datapack golden capture under
  the two-tier parity gate

### Requirement: Whole-chunk vanilla fallback

On encountering an extension the core cannot interpret (a Java-registered
feature, an unknown schema construct), the core MUST fall back to the vanilla
path for the **whole chunk** (ADR-003 D5). Fallback granularity MUST NOT be
smaller than a chunk: partial fallback breaks RNG consumption order. The core
never guesses at unknown extensions; correctness outranks speed.

#### Scenario: Unknown Java feature registered

- **GIVEN** a mod registers a Java-coded feature unknown to the core
- **WHEN** a chunk whose generation touches that feature is requested
- **THEN** that entire chunk is generated by the vanilla path and the
  combined output still satisfies parity

#### Scenario: Sub-chunk fallback attempt

- **WHEN** a change introduces fallback at feature or section granularity
- **THEN** it is rejected: RNG consumption order across the chunk would
  diverge from vanilla
